## مقایسه روش‌های اتصال (تحلیل صادقانه)

| معیار | EA + TCP محلی (انتخاب‌شده) | کتابخانه رسمی Python MetaTrader5 | فایل/MSMQ و مشابه |
|---|---|---|---|
| دریافت رویداد | Event-driven با OnTradeTransaction — در حد چند میلی‌ثانیه | ندارد؛ باید poll کنید (۵۰-۲۰۰ms+ تأخیر عملی) | Poll-based، کند |
| اتصال به ترمینال لاگین‌شده | بله، بدون رمز عبور | بله با initialize(path) اما هر پروسه Python فقط یک ترمینال | بله |
| چند ترمینال هم‌زمان | نامحدود (هر EA یک سوکت) | ممکن اما نیازمند مدیریت چند پروسه + صف‌ها | ممکن |
| تغییرات سریع SL/TP و Partial | فوری (رویداد) | با تأخیر poll | کند |
| وابستگی | فقط کتابخانه استاندارد MT5 | نصب Python + ماژول رسمی (فقط ویندوز) | - |
| ریسک اصلی | باز بودن یک چارت با EA در هر ترمینال (ساده) | نسخه‌های ماژول، قفل شدن IPC ترمینال | شکننده |

**نتیجه:** برای «کمترین تأخیر عملی + پایداری + بدون نگهداری رمز» معماری EA+TCP بهترین تعادل است. ماژول Python می‌تواند به‌عنوان منبع دوم اطلاعات حساب استفاده شود اما برای موتور رویداد مناسب نیست.

## جریان یک معامله کپی‌شده (با زمان‌سنجی واقعی)

1. معامله در مستر باز می‌شود → ترمینال رویداد `TRADE_TRANSACTION_DEAL_ADD` می‌دهد.
2. EA آن را به JSON تبدیل و در صف خروجی می‌گذارد (بدون بلاک شدن) → `{"type":"event","event":"position_opened",...}`
3. موتور رویداد را دریافت می‌کند → `detectedAt` ثبت می‌شود.
4. برای هر اسلیو به‌صورت موازی: فیلترها → نگاشت نماد → محاسبه حجم → `send` → `sentAt`.
5. EA اسلیو سفارش را اجرا و `ack` می‌فرستد → `ackAt` (تأخیر = ackAt − detectedAt).
6. موتور دفتر کپی و متریک را به‌روزرسانی می‌کند → `doneAt` (کل = doneAt − detectedAt).
7. داشبورد از `/api/state` و `/api/copies` این اعداد را نشان می‌دهد.

## Idempotency (جلوگیری قطعی از سفارش تکراری)

- **لایه موتور:** جدول `copy_ops` دارای قید `UNIQUE(slave_terminal_id, event_key)` است. event_key برای باز کردن معامله `open:{masterTicket}` است؛ تکرار رویداد یا اجرای مجدد موتور هرگز ردیف دومی نمی‌سازد.
- **لایه EA:** پیش از باز کردن سفارش، پوزیشن‌ها/سفارشات از نظر کامنت `MC:{eventKey}` اسکن می‌شوند؛ اگر موجود باشد، همان تیکت موجود ack می‌شود نه سفارش جدید.
- **Restart:** رویدادها replay نمی‌شوند؛ موتور از Snapshot ترمینال‌ها وضعیت را بازسازی و فقط Drift را طبق سیاست گزارش/اصلاح می‌کند.

## همگام‌سازی و Drift

سناریوها (اسلیو آفلاین در لحظه معامله، رد شدن توسط بروکر، بسته شدن مستقل اسلیو توسط SL بروکر و...) در جدول `copy_ops` با وضعیت `missed/failed/skipped` ثبت می‌شوند. پس از اتصال مجدد اسلیو:

- سیاست `report` (پیش‌فرض): فقط لاگ و هشدار — هیچ سفارشی خودکار زده نمی‌شود.
- سیاست `autoOpenMissing`: معاملات جاافتاده باز می‌شوند (از طریق همان خط‌لوله idempotent).
- سیاست `autoCloseExtra`: پوزیشن‌های بدون معادل مستر بسته می‌شوند.
- در داشبورد برای هر اسلیو دکمه‌های دستی «باز کردن جاافتاده‌ها» و «بستن اضافی‌ها» وجود دارد (تأیید انسانی).

## امنیت

- همه ترافیک روی `127.0.0.1` است؛ هیچ داده‌ای به اینترنت نمی‌رود.
- رمز عبور حساب خوانده یا ذخیره نمی‌شود؛ اتصال از ترمینال‌های از قبل لاگین‌شده است.
- در صورت نیاز به ذخیره تنظیمات حساس در نسخه‌های بعدی، از DPAPI ویندوز استفاده خواهد شد (ساختار کد آماده است).
- توقف اضطراری به‌صورت پیش‌فرض فقط کپی را متوقف می‌کند (`halt`)؛ بستن پوزیشن‌ها فقط با سیاست صریح کاربر.

## رابط کاربری جدا از موتور

داشبورد فقط REST مصرف می‌کند؛ اگر مرورگر هنگ کند یا بسته شود، موتور و کپی معاملات بی‌تغییر به کار ادامه می‌دهند.
